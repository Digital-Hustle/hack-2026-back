# PreProcessor — CSV → проверенные операции с категориями → JSON

Самостоятельный микросервис Java 21 / Spring Boot 3.5.7. Без БД, JWT, внешнего ИИ, расчёта прогноза и определения регулярности. Сборка расположена внутри сервиса и не изменяет корневую сборку или соседние модули.

## Запуск

Из `services/preprocessor/`, нужен JDK 21:

```powershell
# Windows: JAVA_HOME должен указывать на установленный JDK 21
.\gradlew.bat clean check bootJar
java -Xmx1536m -jar build\libs\preprocessor.jar
```

```bash
# Linux / macOS
./gradlew clean check bootJar
java -Xmx1536m -jar build/libs/preprocessor.jar
```

Gradle Wrapper 8.14.2 включён, SHA-256 дистрибутива проверяется. Первая сборка требует доступа к Maven Central и Gradle distributions. У проекта с кириллицей в пути на некоторых Windows/JDK возникают ошибки classpath; в таком окружении используйте checkout/worktree с латинским путём.

По умолчанию сервер доступен только на **127.0.0.1:8082**. `GET /health` возвращает `{"status":"UP"}`. Не публикуйте этот порт как пользовательский API: здесь ещё нет проверки доступа через Orchestrator. Для закрытой сервисной сети можно явно настроить `PREPROCESSOR_BIND_ADDRESS`, но сетевую изоляцию должен обеспечить деплой.

## HTTP-интерфейс

```text
POST /internal/v1/statements/prepare
Content-Type: multipart/form-data
file: обязательная CSV-выписка
companies: необязательный CSV-справочник компаний
```

Пример для предоставленных локальных файлов:

```powershell
curl.exe --fail-with-body `
  -F "file=@C:/Users/xxx/Desktop/mocks/statements/C001.csv" `
  -F "companies=@C:/Users/xxx/Desktop/mocks/companies.csv" `
  -o "C:/Users/xxx/AppData/Local/Temp/opencode/prepared-C001.json" `
  "http://127.0.0.1:8082/internal/v1/statements/prepare"
```

Вместо `C001.csv` можно передать `all_operations.csv`. **Не загружайте общий файл и все отдельные выписки как разные источники:** это одни и те же операции. В этой версии не хранятся прошлые импорты — дедуп между запросами обязан выполнять получатель JSON.

`200` означает, что файл разобран и возвращён отчёт, **не** что данные сохранены. Проверяйте `report.status`:

| Статус | Значение |
|---|---|
| `PREPARED` | Все строки операций корректны; предупреждения всё ещё возможны |
| `PARTIAL` | Часть строк отклонена или есть некорректные записи справочника |
| `INVALID` | Нет корректных операций; смотреть `report.issues` |

При структурной ошибке файла или превышении лимита возвращается `application/problem+json`: `400` — нет поля `file`, `413` — слишком большой файл/слишком много строк, `415` — не CSV/не UTF-8/не multipart, `422` — повреждённый CSV или другие файловые ошибки. Ответ содержит `code`, безопасное описание, `sourceLine` и `requestId`. Содержимое ошибочного поля не вставляется в сообщение.

## Формат CSV

UTF-8, допускается BOM. Разделитель `;`, заголовок обязателен. Кавычки, `;` и переносы внутри кавычек разбирает Apache Commons CSV, не `String.split`.

Выписка — обязательные **колонки**:

```text
company_id;operation_id;operation_date;amount;direction;counterparty_inn;counterparty_name;payment_purpose;balance_eod
```

Справочник — если передан:

```text
company_id;company_name;company_inn;legal_form;industry;first_operation_date;last_operation_date;operations_count
```

Колонки сопоставляются без учёта регистра и крайних пробелов; произвольный порядок допустим. Дополнительные колонки не теряются: их исходные значения входят в `sourceFields`. Исходные значения сохраняются после CSV-декодирования, а не как побайтовая копия строки с кавычками. CSV компании нужен только для сопоставления по внешнему `company_id`; это **не подтверждение владения компанией**.

## Валидация

- Непустые идентификаторы до 128 символов; операция идентифицируется парой `company_id + operation_id`.
- Существующие даты `YYYY-MM-DD`, годы 1–9999, дата не позже текущего дня в настроенном часовом поясе.
- `amount` строго положителен. Десятичная точка, не более двух знаков после неё, диапазон `NUMERIC(19,2)`. `NaN`, экспоненциальная запись, ноль и отрицательная сумма отклоняются. Лишние копейки не округляются молча.
- `balance_eod` может быть отрицательным (овердрафт) или пустым. Пустой остаток остаётся `null`, а не превращается в ноль.
- Направление `Поступление`/`Списание` или `IN`/`OUT`.
- ИНН — строка из 10 или 12 цифр либо пустое значение. Ведущие нули сохраняются. Контрольная сумма не проверяется, поскольку входной датасет использует вымышленные ИНН.
- Имя контрагента до 500 символов, назначение до 2000; неизвестные поля тоже ограничены по длине. Нулевые и недопустимые управляющие символы не принимаются.
- Пустые ИНН, назначение и остаток дают предупреждения. Операция не выдумывается и не удаляется только из-за отсутствия необязательных данных.
- В справочнике проверяются название, формат ИНН, ООО/ИП, даты и их порядок, неотрицательное целое `operations_count`. Этот счётчик сохраняется как метаданные: он не сравнивается с отдельной частичной выпиской.
- Если справочник передан, ссылка на неизвестную/конфликтующую компанию отклоняется. Без справочника возвращаются внешние ID компаний, без выдуманных названий и реквизитов.
- При одинаковом ID и одинаковых исходных полях повтор пропускается с предупреждением. При разных данных одного ID обе версии исключаются. Похожие платежи с **разными** ID сохраняются и отмечаются `POSSIBLE_DUPLICATE`.
- По компании и дню суммируются поступления/расходы, но повторяющийся EOD берётся один раз. Разные EOD одного дня дают `CONFLICT` и `null` в дневном якоре; значения исходных операций остаются доступными.
- Переход к следующему наблюдению проверяется с допуском 0.01. Несовпадение даёт предупреждение о возможной неполноте данных, не создаёт «исправляющий» платёж.
- Интервал более 7 дней между наблюдениями отмечается `HISTORY_GAP`. Дни без строк не добавляются автоматически: это может быть отсутствие операций, праздник, закрытие счёта или пропуск выгрузки.

У ошибки есть `source` (`STATEMENTS`/`COMPANIES`), номер CSV-записи `sourceRecord`, физическая строка начала `sourceLine`, поле и причина. Для ошибок записи сохраняется первая обнаруженная проблема поля; для структурных ошибок обработка файла прекращается, чтобы не вернуть повреждённые данные как успешный результат.

## Категоризация

`RuleCategorizer` использует упорядоченные правила по направлению и смыслу назначения, без конкретных ID/ИНН из датасета и без ИИ. Для поиска нормализуются регистр, `ё/е`, Unicode и пробелы. Исходное назначение сохраняется.

Категории включают выручку (эквайринг, СБП, наличные, маркетплейсы, клиенты), зарплату, налоги, комиссии, внутренние переводы, финансирование владельца, возвраты, кредиты, лизинг, аренду, топливо, транспорт, ремонт, поставщиков, коммунальные услуги, связь, ПО, бухгалтерию, охрану, уборку, рекламу, подрядчиков, канцтовары и оборудование.

Специальные правила возвратов/переводов/кредитов идут раньше общего правила оплаты. Упоминание НДС внутри закупки не превращает её в уплату налога. Комиссия и возвраты, перечисленные внутри эквайрингового поступления, не вычитаются повторно из `amount`. Одно имя банка не определяет категорию. Погашение кредита остаётся одной операцией, даже если текст содержит тело и проценты.

У категории есть `code`, русский `title`, `source`, `ruleId`, `rulesVersion`, `needsReview`. Неизвестное: `OTHER`, `UNCLASSIFIED`, `ruleId=null`, `needsReview=true`. Процент уверенности не выдумывается. **Поля регулярности отсутствуют.** Правила эвристические: покрытие не равно точности, возможны ошибки, нужен независимый ручной eval.

## JSON и передача дальше

`docs/JSON.md` показывает пример ответа. Корневой объект содержит:

- `schemaVersion` и `rulesVersion`;
- SHA-256 `inputFingerprint` от содержимого входных файлов с разграничением частей;
- `preparedAt`;
- `companies` — справочник или только ID при его отсутствии;
- `operations` — все корректные исходные поля и категория, номера строк, `sourceFields`;
- `dailyBalances` — наблюдаемые дневные агрегаты с качеством якоря;
- `report` — числа строк, коды проблем, ограниченный список деталей.

Деньги на API-границе — **строки** с двумя знаками. Внутри — `BigDecimal`. Дата и направление нормализуются, их исходные строки также остаются в `sourceFields`.

Сервис сейчас только **подготавливает и возвращает JSON**. Он не отправляет его на несуществующий endpoint Orchestrator, не пишет БД и не заявляет `persisted=true`. Для пользовательского импорта нужен согласованный маршрут: проверка актуального доступа к организации, сопоставление внешних ID, идемпотентное сохранение в Orchestrator, затем подтверждение результата. Это следующая межсервисная задача.

## Лимиты и логи

| Настройка | Значение по умолчанию |
|---|---|
| `PREPROCESSOR_PORT` | 8082 |
| `PREPROCESSOR_BIND_ADDRESS` | 127.0.0.1 |
| `PREPROCESSOR_TIMEZONE` | Europe/Moscow |
| `PREPROCESSOR_MAX_STATEMENT_BYTES` | 104857600 (100 MiB) |
| `PREPROCESSOR_MAX_COMPANY_BYTES` | 2097152 (2 MiB) |
| `PREPROCESSOR_MAX_ROWS` | 250000 на файл |
| `PREPROCESSOR_MAX_FIELD_LENGTH` | 4096, поверх этого есть более строгие лимиты известных полей |
| `PREPROCESSOR_MAX_ISSUES` | 1000 подробностей, счётчики всех проблем сохраняются |
| `PREPROCESSOR_TIMEOUT_SECONDS` | 120 для обработки CSV |

Multipart ограничен 100 MB на файл / 105 MB на запрос. Более строгие лимиты проверяются и в контроллере, и в чтении потока. Изменение лимита приложения вверх не увеличивает multipart-лимит автоматически. Прежний общий лимит 20 MB не подошёл: предоставленный `all_operations.csv` имеет около 64 MB. Для больших файлов JSON содержит и нормализованные, и исходные значения, поэтому ответ значительно больше CSV; рекомендуется обрабатывать компании по отдельности и ограничить параллельные импорты на вызывающей стороне. Таймаут CSV не является жёстким лимитом времени загрузки/отдачи ответа.

Консоль: начало/завершение запроса, случайный `requestId`, HTTP-статус, длительность, числа принятых/отклонённых/неопределённых строк и ошибок. Суммы, ИНН, имена, назначения, содержимое CSV и токены не логируются. В ответе есть `X-Request-Id`. Не включайте body-logging в прокси/HTTP-клиенте.

## Проверки

```powershell
.\gradlew.bat clean check bootJar
```

JUnit: парсер, валидация, категории и негативные случаи. HTTP-тесты поднимают реальный сервер на случайном порту и проверяют multipart/JSON/ошибки/логи. ArchUnit защищает границу бизнес-логики от HTTP DTO/SQL и запрещает float/double в денежной модели. Checkstyle и JaCoCo включены. БД/Docker/Orchestrator для этих тестов не нужны.

Реальный набор пользователя использован только локально и **не добавлен в Git**. На локальном прогоне `all_operations.csv + companies.csv`: 222420 строк приняты, 0 отклонены; категории определены для 214497 строк (96.4%), `OTHER` — 7923. Это покрытие правил, не оценка accuracy. Полный HTTP-прогон занял около 20 секунд с `-Xmx1536m`; JSON около 251 MB. Это единичный локальный замер, не SLA/нагрузочный тест. Сетевая изоляция production и интеграция с Orchestrator не проверены.
