# AGENTS.md — Cashflow backend (hack-2026)

Этот файл — стартовый контекст для разработчиков и AI-агентов, работающих с репозиторием `Digital-Hustle/hack-2026-back`. Прочитайте его **до** изменения кода, контрактов или архитектуры. Он описывает назначение проекта, границы сервисов, инварианты и способ проверки изменений; подробные спецификации остаются в документах по ссылкам ниже.

> Актуальность: базовая редакция от 2026-10-24. Это не сертификат готовности MVP. При расхождении с кодом проверьте реализацию и обновите документацию; не объявляйте функцию работающей только потому, что она описана в ТЗ или draft-контракте.

## 1. Продукт и источники истины

**Продукт:** финансовый помощник для малого бизнеса в экосистеме банка «Центр-инвест» (хакатон «Осень 2026»). На основании истории операций, регулярных потоков и известных будущих платежей приложение должно строить **ежедневный прогноз денежных средств как минимум на 30 дней**, выявлять кассовые разрывы и объяснять риски предпринимателю.

Основной пользователь — предприниматель без специальной финансовой подготовки. Прогноз должен быть не только числом на графике: важны остаток, даты и суммы дефицита, вероятность при наличии достаточных данных, причины и понятные возможные действия.

Источники, в порядке назначения:

1. [Notion: функциональные FR-01–FR-23 и технические требования](https://app.notion.com/p/2026-40212e57118e81d2a0e0dc62a91d2b83) — **что** должен делать продукт. Некоторые разделы Notion описывают **планируемую** более крупную архитектуру, а не текущий код.
2. [`backend-skills/docs/BACKEND_GUIDE.md`](backend-skills/docs/BACKEND_GUIDE.md) — принципы backend и фактически принятая схема из пяти сервисов.
3. [`backend-skills/docs/ORCHESTRATOR_FORECAST_HANDOFF.md`](backend-skills/docs/ORCHESTRATOR_FORECAST_HANDOFF.md) — границы Orchestrator/Forecast, версии, исторические срезы, snapshots, jobs и wire-контракт. В документе есть проектные разделы; сверяйте с текущей реализацией.
4. [Репозиторий API-спецификаций Zapas](https://github.com/Digital-Hustle/zapas) — согласуемые внешние контракты. Изменения API синхронизировать с их актуальной редакцией.

## 2. Текущие границы микросервисов

В **этом репозитории** принята архитектура из пяти сервисов. Не создавайте автоматически отдельные Org, Planning, Integrations или Notification только потому, что они встречаются в ранних схемах Notion: выделение таких сервисов — отдельное архитектурное решение.

| Сервис / каталог | Ответственность | Состояние данных |
| --- | --- | --- |
| **Auth/Profile** — `services/auth-profile` | Email OTP, пользователь и профиль, сессии, JWT, refresh/logout | **Собственная PostgreSQL**; Liquibase, jOOQ |
| **Gateway** — `services/gateway-server` | Внешняя точка входа, маршруты, аутентификация access-cookie, CSRF/Origin, доверенный контекст | Stateless; не владеет финансовыми данными |
| **Preprocessor** — `services/preprocessor` | Приём и проверка CSV, нормализация, rule-based категоризация, предупреждения о качестве, подготовка JSON | Stateless; не сохраняет историю и не принимает решение о правах компании |
| **Orchestrator** — `services/orchestrator` | Компании/членство/счета, импорт и финансовая история, планы/оплаты, решения по регулярностям, версии, snapshots, jobs, сохранённые прогнозы и backtests | **Собственная PostgreSQL**; Liquibase, Spring JDBC |
| **Forecast** — `services/forecast` | Вычисление прогноза, обнаружение кандидатов регулярностей, риски, исторический backtest | Stateless; не обращается к чужой БД и не хранит jobs/результаты |

**Поток данных (логическая схема):**

```text
Frontend -> Gateway -> Auth/Profile
                    -> Preprocessor -- prepare CSV -> JSON
                    -> Orchestrator -- stage/finalize JSON -> PostgreSQL
                                      | immutable input snapshot + job
                                      v
                                 Forecast (calculate / backtest / detect)
                                      |
                                      v
                                 Orchestrator validates & persists
                                      |
                         Gateway -> Frontend reads results
```

Это логический сценарий, **не утверждение о наличии единой автоматической операции загрузки и прогноза**. Сейчас подготовка CSV и его сохранение могут требовать **отдельных запросов**. Наличие внутренних endpoint у Forecast не означает, что соответствующий публичный маршрут, job handler и полный UI-сценарий уже подключены.

Сервис Forecast получает полный immutable snapshot от Orchestrator, **не** JWT и **не** доступ к PostgreSQL. Авторизация, idempotency, запуск/повторы заданий, проверка ответа, staleness и сохранение результата принадлежат Orchestrator.

## 3. Требования MVP (обязательные)

Для задач и PR указывайте соответствующие FR. Реализацию подтверждайте тестами и работающим сквозным сценарием, а не наличием DTO или таблицы.

| FR | Обязательный результат | Основные участники |
| --- | --- | --- |
| FR-01 | Загрузка истории банковских операций | Preprocessor + Orchestrator + Gateway |
| FR-02 | Категоризация поступлений и списаний | Preprocessor; Orchestrator хранит категории/правки |
| FR-03 | Поиск **кандидатов** регулярных потоков и возможность их подтвердить | Forecast (detector) + Orchestrator (запуск, merge, решения) |
| FR-04 | Учёт **известных будущих обязательств** (счета, налоги и др. из внешних данных) | Orchestrator; базовый структурированный импорт обязателен, сложные коннекторы — отдельно |
| FR-05 | Прогноз будущих поступлений и списаний | Forecast + Orchestrator |
| FR-06 | Остаток на **каждый день** горизонта не менее 30 дней | Forecast + API Orchestrator |
| FR-07 | Обнаружение будущих кассовых разрывов | Forecast |
| FR-08 | Дата, сумма нехватки и **вероятность** риска | Forecast; если вероятность не рассчитана, явно отражать неполноту, не выдумывать число |
| FR-09 | Список предупреждений о рисках | Orchestrator/API + Frontend |
| FR-10 | График ожидаемого остатка по дням | Frontend на основе результатов backend |
| FR-11 | Объяснение причины/времени/суммы разрыва и возможных действий | Forecast/Orchestrator + Frontend |

Дополнения **FR-12–FR-23**: договоры, счета, налоговый календарь, план-факт, просрочки, пересчёт при отклонениях, сценарии «что если» и их сравнение, банковские/внешние интеграции (включая 1С), ручные будущие события, источник и актуализация. Их нужно учитывать в модели данных и расширяемости, но **не подменять ими обязательный MVP**. Точные формулировки — в Notion.

Технический минимум: работающий прототип, реально применяемая категоризация, модель/алгоритм **с проверкой качества на исторических данных**, график и предупреждения. **Обучение ML-модели не является обязательным само по себе**; воспроизводимость прогноза и честная оценка качества обязательны.

## 4. Демонстрационный сценарий

Проверяемый пользовательский путь:

1. Авторизоваться, создать/выбрать компанию и счёт с соответствующими правами.
2. Загрузить CSV через Preprocessor; изучить `report`, ошибки, категории, дубликаты и качество остатков.
3. Передать подготовленный JSON в импорт Orchestrator, выполнить **атомарный finalize** и проверить фактическую историю.
4. Запустить detection регулярностей, показать кандидатов; пользователь подтверждает или исключает их.
5. Добавить известные будущие обязательства; сформировать snapshot и прогноз на 30 дней.
6. Получить ежедневные остатки, риски, предупреждения, объяснения; выполнить backtest и показать качество.
7. Для расширенного сценария — частичная оплата/задержка, актуализация прогноза, «что если» и сравнение.

**Текущие зоны, требующие отдельной end-to-end проверки:** публичный запуск и полный polling цикла detection, структурированный импорт внешних обязательств, численно корректная вероятность риска, объяснения/рекомендации, сквозная связка Gateway → Preprocessor → Orchestrator → Forecast. Проверяйте статус по последним merged PR: это список контрольных точек, а не неизменное утверждение, что каждая функция отсутствует.

## 5. Данные организаторов и финансовые инварианты

Тестовый набор — `cashflow_dataset_participants.zip` ([ссылка на источник в Drive](https://drive.google.com/file/d/1OCefhmoOMrr2dkBPogbNp79eVIDIAu_v/view)): **150 компаний, 222 420 операций, 2024-10-01 — 2026-09-30**. `all_operations.csv` и отдельные `statements` представляют пересекающиеся/те же операции: **не импортируйте оба набора как новые факты**. Данные для тестов в репозиторий не коммитить.

Инварианты, которые нельзя нарушать при рефакторинге:

- **Деньги:** `BigDecimal`/PostgreSQL `numeric`, никогда `float`/`double`; на JSON-границах согласованный десятичный формат, без потери копеек. В v1 прогноз делается для **одного RUB-счёта**, без неявной консолидации.
- **Идентичность операций:** внешние ID привязаны к источнику, компании и счёту; ретраи идемпотентны. Совпадение суммы/даты/контрагента при разных ID — **не** достаточная причина удалить платеж. Конфликт одного ID с разным содержимым нельзя молча игнорировать.
- **Неполная история:** отсутствие операции за день не доказывает, что день нулевой. Различайте `OBSERVED`, `ZERO_CONFIRMED`, `MISSING`. Через неизвестный интервал нельзя произвольно переносить остаток.
- **`balance_eod`:** остаток **на конец дня**, часто повторяется в нескольких строках дня; брать один согласованный EOD, не суммировать. При несовпадении с предыдущим EOD и чистыми потоками создавать issue/предупреждение, не искусственный платёж.
- **Поля источника:** ИНН — строка (сохранить ведущие нули), реквизиты/назначение могут отсутствовать. Не выводить из ZIP несуществующие номер счёта, валюту, КПП или налоговый режим; необходимые сведения задаются контекстом.
- **Факт, план и прогноз — разные сущности.** Подтверждённая регулярность, покрытая известным обязательством, не учитывается повторно. При частичной оплате в будущем учитывается **оставшаяся** сумма. Просрочку не переносить автоматически на следующий день.
- **Историческое знание:** `operationDate`, `knownAt`, `asOfDate` и момент построения — разные оси времени. Backtest не должен видеть платежи, редакции, планы и подтверждения, ставшие известными позже cutoff.
- **Версии:** `dataVersion` отражает изменение входов компании, `version` конкретной сущности — optimistic locking, `snapshotId` обозначает конкретный audit snapshot, `fingerprint` — содержимое для вычисления. Не смешивать их.
- **Расчёт:** snapshot immutable и согласован на одном MVCC-срезе; Forecast считает, Orchestrator валидирует и сохраняет. Повтор job не должен создавать второй результат.

Принципы и wire-форматы подробнее: [handoff](backend-skills/docs/ORCHESTRATOR_FORECAST_HANDOFF.md), [Orchestrator README](services/orchestrator/README.md), [Forecast README](services/forecast/README.md), [Preprocessor README](services/preprocessor/README.md).

## 6. Безопасность и trust boundaries

- Проверка JWT/cookies, CSRF/Origin и очистка недоверенных клиентских заголовков — на Gateway. Downstream получает **только доверенный** `X-User-Id` (при необходимости контекст сессии) по **закрытой сети**; эти заголовки от клиента не являются доказательством личности.
- Orchestrator **в каждом** финансовом запросе проверяет членство и право на `companyId/accountId`. Внешний `company_id` из CSV — сопоставление данных, **не** выбор владельца и не основание для авторизации.
- Межсервисные `/internal/**` не выставлять наружу; Forecast доступен только Orchestrator. Stateless не значит публичный.
- Не логировать тела выписок/финансовых запросов, ИНН, секреты, токены, SMTP-коды, полные payload snapshots. Не добавлять реальные данные организаторов и `.env` в Git.
- Для mutating API соблюдайте `If-Match`, `Idempotency-Key` и согласованные ошибки; не ослабляйте проверки для удобства тестирования.

## 7. Правила изменений

1. **Сначала прочитать** этот файл, README изменяемого сервиса, [backend guide](backend-skills/docs/BACKEND_GUIDE.md) и релевантные разделы [handoff](backend-skills/docs/ORCHESTRATOR_FORECAST_HANDOFF.md). Перед правкой API смотреть существующие OpenAPI/контракты в Zapas. Договорённости и фактическую архитектуру не заменять устаревшей схемой из Notion.
2. **Соблюдать ответственность сервиса.** Preprocessor не пишет бизнес-БД; Forecast не проверяет членство и не пишет результаты; Orchestrator не дублирует алгоритм прогноза; Gateway не реализует финансовую логику. Не добавлять брокер, Config Server, новую БД или ML-инфраструктуру без отдельного обоснованного требования.
3. **Следовать существующему стилю конкретного модуля.** В проекте Java 21 / Spring Boot / Gradle Kotlin DSL; feature-first, тонкие HTTP-контроллеры, явные application-команды/запросы, DTO records, Bean Validation. Использовать MapStruct, Lombok builders, jOOQ или Spring JDBC согласно **реальному** стеку сервиса; не вносить технологию из соседнего сервиса механически. Избегать magic numbers, скрытых побочных эффектов и переусложнённых abstractions.
4. **Сначала определить контракт и инварианты**, затем реализацию. При изменении поведения добавить unit-, API-/contract- и, где критично, интеграционные тесты: импорт/idempotency, версионирование, неизвестные дни, балансные расхождения, частичные оплаты, исторические cutoff, retries и безопасность.
5. **Проверять то, что изменили.** Для модульного Gradle-проекта из корня: `bash gradlew :services:<service>:test :services:<service>:build --continue --no-daemon`; на Windows — `.\gradlew.bat`. Пример сквозной проверки JSON Preprocessor ↔ Orchestrator: `PREPROCESSOR_SAMPLE_JSON` для `PreprocessorContractTest` (без него этот тест может быть пропущен). Отдельно проверять подключение реальных сервисов: мок HTTP или зелёный CI **не доказывают** end-to-end готовность.
6. **Изменения через небольшой отдельный PR.** Указывать затронутые FR, изменённые публичные/внутренние контракты, миграции, тесты и ограничения. Не сливать PR без явного запроса. Если проверку не запускали — сообщить об этом; не выдавать draft документа за выполненную функцию.
7. **Обновлять документацию при изменении поведения**: README сервиса, handoff, Zapas/OpenAPI и этот `AGENTS.md`, если поменялись архитектура, границы ответственности или сценарий работы.
