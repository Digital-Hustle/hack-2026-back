# Сотрудники и зарплата

API через Gateway: `/api/v1/orchestrator/companies/{companyId}/employees`.
OWNER/ACCOUNTANT создают и изменяют сотрудников и выплаты; VIEWER может читать.
Карточка сотрудника — бизнес-данные компании, а не пользователь или участник приложения.
Затронуты FR-04–FR-06: известные регулярные списания и ежедневный прогноз.

## Контракт

| Метод и путь относительно employees | Результат |
|---|---|
| `POST /` | Создать карточку, `201 Employee`; обязателен `Idempotency-Key` |
| `GET /?includeArchived=false&page=0&size=50` | `{items: Employee[], page: {page,size,total,hasNext}}`; size 1..200 |
| `GET /{employeeId}` | Карточка, в том числе архивная, `200 Employee` |
| `PUT /{employeeId}` | Изменить ФИО, должность, заметку, `200 Employee` |
| `PUT /{employeeId}/salary` | Создать/обновить подтверждённую зарплату, `200 Employee` |
| `PUT /{employeeId}/recurring-payment` | Привязать и подтвердить существующее регулярное списание, `200 Employee` |
| `DELETE /{employeeId}/recurring-payment` | Исключить выплату и убрать связь, `200 Employee` |
| `POST /{employeeId}/archive` | Архивировать сотрудника и исключить его регулярную выплату, `200 Employee` |

Все изменения существующей карточки требуют `If-Match: "<Employee.version>"`.
Версия Employee начинается с **1**. Версия вложенного recurringPayment начинается с **0**, как
у действующего API регулярностей. Используйте значения из ответа, не вычисляйте их на фронте.
Создание сотрудника требует ключ 8..128 символов `[A-Za-z0-9_.:-]`. Одинаковый ключ с одинаковыми
нормализованными полями возвращает ту же карточку (текущее состояние); другое содержимое — `409`.
PUT защищён версиями: повтор с прежней версией вернёт `409`, вторую зарплату он не создаст.
На Gateway для мутаций также обязательны access-cookie, Origin, CSRF-cookie и X-CSRF-Token.

## Карточка

Тело POST/PUT:

```json
{
  "fullName": "Иван Петров",
  "position": "Разработчик",
  "note": "Оклад за полный месяц"
}
```

`fullName` обязателен, непустой, до 500 символов; `position` до 200; `note` до 1000.
PUT заменяет эти три поля; пропущенные необязательные поля очищаются.

Ответ `Employee`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "companyId": "22222222-2222-4222-8222-222222222222",
  "fullName": "Иван Петров",
  "position": "Разработчик",
  "note": "Оклад за полный месяц",
  "archived": false,
  "recurringPayment": null,
  "version": 1,
  "createdAt": "2026-10-25T07:00:00Z",
  "updatedAt": "2026-10-25T07:00:00Z"
}
```

После назначения `recurringPayment` содержит существующий `RecurringPatternRs`:
`id`, `accountId`, `direction`, `categoryCode`, `counterpartyKey`, `status`, `statusSource`,
`schedule`, `amount` (строка с двумя десятичными знаками), `observations`, `firstSeen`, `lastSeen`,
`inputDataVersion`, `detectorVersion`, `version` и новый `employeePayment: true`.
Статус вложенной регулярности следует читать из актуального ответа: её также можно исключить через
существующий API `/recurring-patterns/{id}/status`.

## Создать или изменить зарплату

`PUT /{employeeId}/salary`, `If-Match: "1"`:

```json
{
  "accountId": "33333333-3333-4333-8333-333333333333",
  "amount": "85000.50",
  "counterpartyInn": "123456789012",
  "counterpartyName": "Иван Петров",
  "schedule": {
    "frequency": "MONTHLY",
    "weekday": null,
    "dayOfMonth": 10,
    "businessDayRule": "FOLLOWING"
  }
}
```

- Создаётся одна обычная `CONFIRMED/USER` регулярность `OUT`, категория `SALARY`, валюта счёта RUB.
- Сумма строго положительная, до 17 цифр до запятой и двух после. Лишние ненулевые знаки отклоняются,
  округления или преобразования через floating point нет.
- `MONTHLY`: dayOfMonth 1..31, weekday null. Короткий месяц использует последний день месяца.
  `WEEKLY`: weekday 1..7 (понедельник..воскресенье), dayOfMonth null.
- businessDayRule обязателен: `NONE` или `FOLLOWING` (перенос субботы/воскресенья на понедельник;
  государственные праздники этим правилом не переносятся).
- Укажите ИНН (10/12 цифр) или имя получателя **как в операциях**. ИНН приоритетнее имени.
  Имя карточки само по себе не считается установленной связью с банковской историей.
- Повторное изменение суммы/расписания требует также `recurringPatternVersion` из вложенного платежа.
  Например, следующий PUT с `If-Match: "2"` содержит прежние реквизиты, новую сумму и
  `"recurringPatternVersion": 0`. ID регулярности сохраняется.
- Счёт, получатель и категория уже связанной зарплаты не меняются этим PUT: сначала отключите выплату,
  затем создайте или привяжите другую. Это сохраняет идентичность истории и связанных планов.
- Если такой поток `(account, SALARY, OUT, counterpartyKey)` уже существует, API вернёт
  `409 RECURRING_ALREADY_EXISTS`: используйте привязку, чтобы не дублировать прогноз.

## Привязать существующий постоянный платёж

`PUT /{employeeId}/recurring-payment`, `If-Match: "1"`:

```json
{
  "accountId": "33333333-3333-4333-8333-333333333333",
  "recurringPatternId": "44444444-4444-4444-8444-444444444444",
  "patternVersion": 0
}
```

Подходит для кандидата из detection и уже подтверждённого/исключённого платежа. Операция явно подтверждает
регулярность от имени пользователя. Направление только OUT; необходим определённый counterpartyKey.
Категория может быть SALARY или другой категорией постоянного вознаграждения. Сумма и расписание
сохраняются; новая регулярность и новый факт не создаются. На одного сотрудника приходится одна
регулярная выплата; одна регулярность может принадлежать только одному сотруднику. Перед заменой
нужно вызвать DELETE recurring-payment. Архивная связь сохраняется и не отдаётся другому сотруднику.

## Прогноз и история

Ручная зарплата учитывается сразу: `detectorVersion=MANUAL_V1`, `observations=0`,
`firstSeen=lastSeen=null`. Это заданное пользователем правило, а не обнаруженные исторические платежи.
Для обычных обнаруженных регулярностей по-прежнему обязательны минимум три наблюдения и даты.

Изменения выплат атомарно обновляют регулярность, append-only revision, аудит, версию сотрудника
и `companies.dataVersion`. Текущий прогноз становится устаревшим; новый запуск использует новое правило
(также работает существующий auto-refresh). ФИО/должность/заметка сами по себе не меняют финансовые входы.
При историческом backtest правило видно только начиная с фактического момента его создания/редакции.
Старые snapshots и результаты не переписываются. ФИО/заметки не передаются в Forecast.

Поток с `employeePayment=true` заменяет историческую группу `(direction, categoryCode, counterpartyKey)`
**на данном счёте**. Операции этого получателя с неопределённой категорией (`OTHER`,
`UNKNOWN`, `UNCATEGORIZED`, `UNCLASSIFIED`) также исключаются из baseline. Операции с явно иной
категорией автоматически не исключаются: сперва проверьте и исправьте их категоризацию.
Будущие суммы берутся из расписания. Поэтому старый оклад, несколько выплат или изменение суммы не добавляются к новой зарплате.
Другие категории/получатели сохраняются. Для банковского общего зарплатного реестра без разбивки по
получателям необходима предварительная явная привязка/разбивка; совпадения по одному ФИО не угадываются.

DELETE связи и archive создают `EXCLUDED` revision. Такое employee-правило остаётся в snapshot только
для исключения старой зарплаты из baseline, будущих регулярных списаний по нему нет. При archive карточка
остаётся доступна через GET и includeArchived; её редактирование и повторное подтверждение связанного
правила запрещены. Восстановление из архива в этой версии не предусмотрено.

Известный отдельный план `REPLACES_RECURRING` заменяет один календарный экземпляр, учитывается его
неоплаченная часть. Уже заведённый финальный расчёт/долг остаётся в прогнозе даже после архивирования;
архивирование не аннулирует обязательства и не создаёт фиктивные фактические выплаты.

В этой версии один поток на сотрудника, без отдельного аванса и оклада, НДФЛ/взносов, расчёта по табелю,
автоматического начисления факта и запланированного изменения оклада с будущей даты. Фактическая выплата
приходит из истории или вводится через обычный API ручного платежа.

## Ошибки

Общий формат — `application/problem+json`, поля `code`, `detail`, `errors`, `traceId`.

| HTTP / code | Причина |
|---|---|
| `401` | Нет доверенного пользователя/валидной access-cookie |
| `403` | VIEWER изменяет данные; компания или счёт архивированы |
| `404` | Чужая/несуществующая компания, карточка, счёт или регулярность |
| `428 PRECONDITION_REQUIRED` | Нет If-Match/Idempotency-Key |
| `428 PATTERN_VERSION_REQUIRED` | При изменении зарплаты нет recurringPatternVersion |
| `409 VERSION_CONFLICT` | Устаревшая версия карточки или регулярности |
| `409 IDEMPOTENCY_KEY_REUSED` | Ключ создания повторно использован с другими полями |
| `409 RECURRING_ALREADY_EXISTS` | Поток зарплаты уже существует; используйте привязку |
| `409 PAYROLL_ALREADY_LINKED` | У сотрудника/регулярности уже есть другая связь |
| `422 EMPLOYEE_ARCHIVED` | Изменение архивной карточки/включение её зарплаты |
| `422 PAYROLL_DIRECTION` | Попытка привязать IN |
| `422 PAYROLL_IDENTITY_CHANGED` | Изменяется идентичность связанной зарплаты |
| `422 INVALID_SCHEDULE / INVALID_AMOUNT / COUNTERPARTY_REQUIRED` | Некорректное расписание, сумма или получатель |
