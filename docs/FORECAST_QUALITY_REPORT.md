# Контрольный прогон: прогноз, логи расчёта и метрики качества

Документ описывает, как на контрольном датасете организаторов получить: пошаговый лог расчёта,
результат прогноза, метрики (Accuracy, Precision, Recall, F1, MAE, MSE, RMSE, WAPE, skill score,
Brier, калибровка вероятностей), матрицы ошибок и данные для графиков «прогноз против факта».

## 1. Последовательность шагов (через Gateway)

Все пути относительно `/api/v1/orchestrator/companies/{companyId}/accounts/{accountId}`,
кроме импорта. Мутирующие запросы требуют cookie-сессию, `X-CSRF-Token` и `Idempotency-Key`.

| # | Запрос | Что происходит |
|---|---|---|
| 1 | `POST /api/v1/preprocessor/companies/{companyId}/imports` (CSV, accountId) → finalize | Загрузка датасета |
| 2 | `POST …/recurring-detection-jobs` `{"asOfDate":"<последняя дата>"}` → polling job | Поиск регулярных платежей |
| 3 | `POST …/recurring-patterns/confirm-detected` | **Новое.** Подтверждает все найденные кандидаты одним действием (иначе в прогноз они не попадают) |
| 4 | `PUT …/forecast-settings` (опционально `"algorithm":"WEEKDAY_ROBUST_V2"`) | Выбор модели |
| 5 | `POST …/forecast-jobs` `{"asOfDate":"…","scope":"HISTORY_ONLY"}` → polling | Прогноз на 30 дней |
| 6 | `POST …/backtest-jobs` `{"asOfDate":"…","firstOrigin":"…","lastOrigin":"…","stepDays":7,"scope":"HISTORY_ONLY","windowWeeks":12,"evaluateRisk":true}` → polling | Проверка качества на истории |
| 7 | см. раздел 2 | Скачивание логов, CSV и отчёта |

Требования к длине истории: одна дата отсечки бэктеста ≈ 12 недель обучения + 30 дней факта
(≈114 дней). Вероятность разрыва и её проверка (Brier, калибровка) требуют ≥12 «зрелых» отсечек
с шагом 7 дней до даты прогноза (≈191 день истории). При нехватке вероятность — `null`
(неизвестна), а не 0.

## 2. Что скачивать

| Endpoint | Формат | Содержимое |
|---|---|---|
| `GET …/forecasts/{id}` | JSON | Прогноз: 30 дней, компоненты, P10/P50/P90, вероятность, эпизоды разрывов, `trace` |
| `GET …/forecasts/{id}/trace` | txt (`?format=json` — JSON) | **Пошаговый лог расчёта**: валидация, окно обучения, исключённые регулярные платежи, уровни по дням недели, формула B(d) для каждого дня, риск, разрывы |
| `GET …/forecasts/{id}/export` | CSV | Дневной ряд прогноза для графика |
| `GET …/backtests/{id}` | JSON | Все метрики, `quality`, `origins[].days[]`, `trace` |
| `GET …/backtests/{id}/report` | Markdown | **Отчёт для жюри**: таблицы метрик, матрицы ошибок, сравнение моделей, выбор модели |
| `GET …/backtests/{id}/trace` | txt / JSON | Лог эксперимента по каждой дате отсечки |
| `GET …/backtests/{id}/export` | CSV | Прогноз против факта по каждой отсечке и дню (график, ошибки, флаги разрыва) |

Расчёт детерминирован: повтор на том же снимке даёт те же числа и тот же лог (seed bootstrap
выводится из fingerprint снимка). Лог не пишется в серверные логи — он часть сохранённого результата.

## 3. Метрики и как их читать

**Ошибка остатка** (по всем парам «отсечка × день горизонта»):
MAE, MSE (₽²), RMSE, WAPE = Σ|ошибка| / Σ|факт|, ошибки по горизонтам 1…30,
MAE дневных входящих и исходящих потоков отдельно (баланс накапливает ошибку, потоки — нет).

**Skill score** = 1 − MAE / MAE(наивная модель «остаток не меняется»). > 0 — модель полезнее
наивной. В `quality.benchmarks` на тех же днях считаются:

- `NAIVE_LAST_BALANCE` — остаток остаётся B(T);
- `SEASONAL_NAIVE_7D` — каждый день повторяет последние известные потоки того же дня недели;
- `WEEKDAY_MEAN_V1@8w/10w/12w`, `WEEKDAY_ROBUST_V2@8w/10w/12w` — наш движок с другим окном и оценщиком.

**Матрица ошибок** (положительный класс — «кассовый разрыв», остаток < 0):

- `quality.primary.dailyMatrix` — по дням: TP/FP/FN/TN, Accuracy, Precision, Recall, Specificity,
  F1, Balanced accuracy, доля разрывов, `majorityBaselineAccuracy`;
- `quality.originMatrix` — по датам отсечки: «будет ли разрыв в ближайшие 30 дней»;
- `quality.bufferDailyMatrix` — то же для порога «ниже буфера», если `bufferAmount > 0`;
- `quality.scenarioDailyMatrix` — классификация по вероятности сценариев `pBelowZero ≥ 0.3`;
- `gapMetrics` — сопоставление эпизодов разрыва один к одному (TP/FP/FN, Precision, Recall, F1,
  заблаговременность, ошибка даты и суммы). TN для эпизодов по построению не определён.

Accuracy без контекста вводит в заблуждение: дней с разрывом обычно мало, и «никогда не
предсказывать разрыв» уже даёт высокую accuracy. Поэтому рядом всегда `majorityBaselineAccuracy`,
Recall, F1 и Balanced accuracy. Если в периоде нет ни одного фактического разрыва, Recall и F1
равны `null` (не определены), а не 100%.

**Вероятности**: Brier score дневной `pBelowZero`, 5 бинов калибровки (средняя прогнозная p против
фактической частоты), покрытие интервала P10–P90 (идеал ≈ 0.8).

**Выбор модели** (`quality.selection`): кандидат (оценщик × окно) выбирается по MAE на ранних
2/3 отсечек, затем его MAE показывается на поздней 1/3, которая в выборе не участвовала.
Это честный ответ на вопрос «какое окно и модель лучше», без подгонки под тестовый период.

Отсечки с шагом 7 дней и горизонтом 30 перекрываются: дневные наблюдения не независимы
(предупреждение `OVERLAPPING_ORIGINS`). MAPE и «100% − MAPE» не используются: остаток бывает
нулевым и отрицательным.

## 4. Модели

`WEEKDAY_MEAN_V1` (по умолчанию): остаток = B(T) + планы + подтверждённые регулярные платежи +
среднее «остаточных» потоков соответствующего дня недели за последние 8/10/12 недель.

`WEEKDAY_ROBUST_V2` (опционально, та же арифметика календаря и планов):

1. официальные нерабочие дни РФ (производственный календарь 2023–2026, для других лет — только
   фиксированные праздники) не входят в выборку дня недели, а в горизонте их остаточный поток = 0;
2. выбросы дальше 3 IQR от квартилей ограничиваются (одна крупная разовая сделка не сдвигает
   прогноз дня недели на 12 недель вперёд);
3. уровни Пн–Пт сжимаются к общему уровню рабочих дней с эмпирико-байесовским коэффициентом
   B = se² / (se² + τ²), где τ² — оценка межднёвной дисперсии. Шумный день недели с малой выборкой
   ближе к общему уровню, устойчивый — остаётся своим.

На синтетических данных с редкими крупными сделками V2 снижал MAE остатка примерно на 5–20%
относительно V1, а на «гладких» данных без выбросов бывал хуже на 1–10%. Универсального
победителя нет, поэтому оба считаются в каждом бэктесте, а выбор делается по `quality.selection`
на реальных данных. Таблицу праздников стоит сверить с официальным постановлением перед защитой.

Отдельно: в прогноз попадают только **подтверждённые** регулярные платежи. Без шага 3
зарплата/аренда размазываются по средним дням недели; на синтетике подтверждение снижало MAE V1
примерно на 6%.
