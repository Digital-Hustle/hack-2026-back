# Ручные фактические платежи

Расширение учёта фактов в Orchestrator; создание будущих обязательств остаётся в expected-payments.
Префикс: `/api/v1/orchestrator/companies/{companyId}`. JWT/CSRF проверяет Gateway.

| Метод | Путь | Доступ | Заголовок |
|---|---|---|---|
| POST | `/payments` | OWNER, ACCOUNTANT | Idempotency-Key |
| POST | `/payments/{id}/void` | OWNER, ACCOUNTANT | If-Match |
| GET | `/payments/{id}/duplicate-candidates` | Все роли компании | — |
| POST | `/payments/{id}/duplicate-resolutions` | OWNER, ACCOUNTANT | If-Match |

Создание (201):
```json
{"accountId":"11111111-1111-4111-8111-111111111111","operationDate":"2026-09-28","amount":"250.00","direction":"OUT","counterpartyName":"Поставщик","categoryCode":"OTHER","note":"Внесено вручную"}
```
Только прошедший день в timezone компании, не CONFIRMED_COMPLETE. source=MANUAL, importId/externalOperationId=null.
Повтор Idempotency-Key с тем же телом возвращает тот же платёж; другое тело — 409.

Аннулирование (200), If-Match содержит точную публичную version из PaymentRs (начиная с 1):
```json
{"reason":"Ошибочная сумма: создам правильный платёж"}
```
Исходная запись сохраняется. Распределения отменяются, остатки планов восстанавливаются через новые revisions.
День переводится в UNKNOWN, dataVersion растёт, проекция пересчитывается. Нет искусственного обратного прихода/расхода.
Из обычных списков фактов и контрагентов аннулированная запись исключается, GET /payments/{id} сохраняется для аудита.
Повтор с прежней версией — 409. Категорию и распределения аннулированного факта менять нельзя.

Кандидаты после finalize импорта: `{items: [PaymentRs]}`, до 200 операций с той же датой, суммой и направлением.
Это предложения для проверки, не доказательство дубля; контрагентов пользователь сравнивает сам.
Подтверждённые пары исключаются из кандидатов. Предупреждение POSSIBLE_DUPLICATE_MANUAL при staging сохраняется.

Решение (200), If-Match — версия ручного факта:
```json
{"importedPaymentId":"22222222-2222-4222-8222-222222222222","importedPaymentVersion":1,"decision":"SAME","reason":"Операция появилась в выписке"}
```
SAME: ручной факт аннулируется, импортированный остаётся действующим. Активные распределения переносятся атомарно;
существующая связь с тем же планом объединяется через reversal и новую запись. При переполнении суммы — 409 и полный rollback.
Полнота импортированного дня сохраняется. DIFFERENT оставляет оба факта. Повтор того же решения по паре идемпотентен,
даже со старым If-Match; противоположное решение — 409. Решения по паре в этой версии окончательные.
Чужая компания/счёт/target — 404, VIEWER при изменении — 403, не ручной источник — 422.

PaymentRs дополнен source, note, status=ACTIVE|VOIDED, voidedAt, voidReason, replacementPaymentId,
dayStatus=OBSERVED|ZERO_CONFIRMED|MISSING, requiresCompletenessConfirmation. Последний признак показывает, что
действующий факт лежит в неполном дне; это не гарантия пригодности всей истории к прогнозу.
Клиент показывает сохранение факта и необходимость проверить день, затем вызывает существующий completeness endpoint.
Один введённый платёж не подтверждает полноту автоматически.

Аннулирование учитывается только при voidedAt < knowledgeCutoff. Исторический input до исправления видит старый факт;
новый input после исправления исключает его. Сохранённые snapshots и результаты не переписываются.
Миграции append-only: прежняя 012-manual-payments подключена после актуальных 012-gap-identities/013-forecast-alerts;
новая 014-manual-payment-corrections хранит события аннулирования и решения по парам.
