# Архитектура cashflow

Принятые пользователем решения для текущего проекта. Это инструкции для реализации, не утверждение о наличии готового кода. Прямые инструкции пользователя и правила среды имеют приоритет.

## Пять сервисов

| Сервис | Ответственность | БД |
|---|---|---|
| Auth + Profile | Пользователи, вход, выпуск/обновление токенов, сессии, профиль человека | Своя |
| Gateway | Проверка JWT, замена входящих заголовков идентификации, маршрутизация без токена | Нет |
| PreProcessor | Приём CSV, проверка, парсинг, нормализация, категоризация, отчёт качества | Нет |
| Orchestrator | Организации, доступ, операции и категории, исправления пользователя, ручные будущие платежи, запуск расчётов, хранение прогнозов и метрик, API фронта | Своя |
| Forecast | Прогноз потоков/остатка на 30 дней, выявление ожидаемого дефицита, историческая проверка качества | Нет |

Не выделять дополнительные ledger/planning/notify/ML-сервисы без нового решения пользователя. Не добавлять CatBoost, обучение ML, брокер, event bus, outbox/inbox, сервисные JWT или обязательные OpenAPI-контракты/генераторы. HTTP DTO и согласованные интерфейсы нужны, но отдельный contract-first процесс не требуется.

## Основные инварианты

1. PreProcessor категоризует; Orchestrator хранит категории и ручные исправления. Forecast не изменяет операции и не обращается к БД Orchestrator.
2. Auth владеет своей БД. Orchestrator владеет всеми бизнес-данными; остальные сервисы работают через HTTP. Профиль человека относится к Auth, организация и её участники — к Orchestrator.
3. Будущий ручной платёж — план, а не факт. Исполненный факт сопоставляется с планом, уменьшая его неоплаченную часть. Одна экономическая операция учитывается в прогнозе один раз.
4. JWT валидирует только Gateway. Бизнес-сервисы получают доверенный контекст без JWT и выполняют проверку ролей/CompanyScope; защита доступа к сервисам основана на сети.
5. Деньги — BigDecimal / NUMERIC(19,2) / строка в HTTP JSON. Остаток на конец дня не суммируется по строкам операций.
6. Прогноз и риск рассчитываются сервером; Orchestrator сохраняет результаты и отдаёт фронту.
7. Проверка качества — повторный запуск того же алгоритма на исторических срезах с горизонтом 30 дней, без будущих данных. «Процент валидации» не заменяет MAE, метрики предупреждений и описание периода проверки.
8. Простой точечный расчёт не выдаёт обоснованную вероятность разрыва. Пока выводить ожидаемую дату/сумму дефицита; не изобретать процент вероятности или точности.
9. Категоризация/регулярности/очистка, если зависят от данных, при бэктесте используют только информацию до отсечки. При отсутствии исторического плана не подставлять сегодняшние планы в прошлое.

## Как применять

Сначала определить владельца изменения по таблице сервисов. Реализовывать фичу в его границах; межсервисные обращения вынести в HTTP-адаптеры. Использовать существующие backend-spring/security/testing навыки как техническое дополнение, а устаревшие архитектурные требования в них не переносить. Не копировать эталон целиком: изучить код, проверить лицензию и адаптировать выбранный паттерн под этот состав сервисов и gateway-auth.

## Проверка реализации

Проверять поведение затронутой части: формат/дедуп и категоризация импорта; права и изоляция организаций; идемпотентность повторной передачи; сопоставление факта с планом; арифметика остатка; неизменность прошлого при прогнозе; отсутствие утечки будущего в бэктесте. Для gateway отдельно проверять подмену заголовков и отсутствие токенов downstream. Запуск тестов не означает, что сеть и развёртывание проверены.
