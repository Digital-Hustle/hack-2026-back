# Простой прогноз и проверка на истории

## Текущий выбор

Forecast — отдельный stateless сервис. Пока без CatBoost и других ML-моделей. Алгоритм реализуется обычным кодом; Java/Spring допустим и согласуется с остальным бэкендом. Python не требуется только ради средних и арифметики.

Вход: дата отсечения T, история доступных операций/ежедневных потоков, остаток B(T), будущие планы с датами/суммами/остатком к оплате, горизонт (по умолчанию 30 календарных дней), параметры окна. Исторический EOD не является прогнозом и не суммируется по операциям.

## Компоненты потока

1. Из истории до T найти подтверждённые регулярные платежи, например зарплату, аренду, кредит. Использовать смысл назначения/категорию и контрагента, а не только название банка. Оценить повторяемость, даты и суммы; нерегулярную операцию не объявлять обязательством.
2. Построить календарь регулярных будущих платежей и вручную добавленных планов.
3. Исторические операции, объясняемые регулярно прогнозируемым календарём, исключить из потока для расчёта средних. Для остальных поступлений и расходов считать отдельные средние соответствующего дня недели по последним 8–12 неделям. Окно — явный параметр, например 12 недель по умолчанию; выбирать на проверках, не заявлять 12 универсально лучшим.
4. Для каждого будущего дня использовать его день недели и доступные значения прошлого. Каждая дата получает прогноз напрямую из истории до T; не подставлять предыдущий прогноз как новый факт.
5. При недостаточной истории считать по доступным подтверждённо полным дням и вернуть low-data предупреждение/число наблюдений. Не выдавать отсутствие наблюдений за нулевую выручку. Короткая история не обрезает требуемый 30-дневный горизонт; отсутствующий компонент явно помечать как недоступный/допущение.

Среднее по понедельникам включает все известные полные понедельники окна, в том числе с нулевым потоком, а не только дни с платежами.

## Двойной учёт

Ручной/известный план, совпадающий с регулярным платежом, заменяет его соответствующий календарный элемент, а не добавляется второй раз. Связи сопоставления должны быть явными.

Если ручной план описывает выручку, уже представленную в среднем остаточного потока, определить является ли он дополнительным или заменяет ожидаемое поступление. Для замены нужен выделенный сопоставимый поток/контрагент и исключение соответствующей базовой части. Без такого разделения нельзя просто прибавлять обычный клиентский платёж к среднему, в котором он уже сидит. Запрашивать уточнение либо показывать допущение, не молча создавать двойной счёт.

Исполненные планы уменьшаются на сопоставленный факт; частичная оплата оставляет только неоплаченную часть. Нельзя вычитать будущий счёт из прошлого без соответствующей исторической операции.

## Остаток и дефицит

Для d = T+1 ... T+30:

B(d) = B(d−1) + plannedIn(d) − plannedOut(d) + regularIn(d) − regularOut(d) + residualIn(d) − residualOut(d).

Все элементы календаря взаимно исключены по экономическому платежу. Деньги считать точно с явным округлением. При B(d)<0 вернуть дату, shortfall=max(0,−B(d)); группировать последовательные отрицательные дни в эпизоды при необходимости. Отрицательный начальный остаток отмечать как существующий дефицит.

Выход: дни с компонентами поступлений/расходов и остатком, дата/сумма ожидаемого дефицита, качество входных данных, параметры, asOf и версия метода. Не выдавать вероятность разрыва и интервалы как измеренные: точечный алгоритм не строит распределения. Стресс-сценарий — условный расчёт, не вероятность.

## Бэктест = rolling-origin time-series cross-validation

Основа: https://otexts.robjhyndman.com/fpp2/toolbox.html#time-series-cross-validation

Один алгоритм используется и для будущего, и для исторических срезов. Разница — дата отсечения.

Пример: история октябрь–июнь → прогноз следующих 30 дней → сравнение с июлем. Затем отсечка в конце июля и следующая проверка. Не смешивать календарный месяц из 31 дня с фиксированным горизонтом 30 дней.

- Выбрать несколько T, для которых есть достаточно истории и фактические следующие 30 дней. Шаг отсечек сделать параметром (например 14 или 30 дней); перекрывающиеся проверки не считать независимыми наблюдениями.
- На каждой T скрыть операции после неё и вызвать тот же прогноз. Регулярности, категории/правила, если обучаются/подстраиваются по истории, заполнение пропусков и любые настройки использовать только на доступном прошлом.
- Фиксированные правила категоризации допускается применять без обучения, если не были подобраны по тестовому будущему. При необходимости повторной подготовки истории Orchestrator обращается к PreProcessor, Forecast остаётся вычислителем.
- Включать только планы, известные на T, в состоянии на T. Если исторических снимков/knownAt нет, проверить history-only режим, а поддержку будущих планов оценивать отдельными сценариями; не подставлять современные планы в прошлое.
- Сравнить прогнозные EOD с фактом для того же счёта и тех же дат. Неполные периоды отдельно учитывать; прогноз не подгонять к фактическому будущему остатку.
- Если подбирается окно 8/10/12 недель, выбрать по ранним validation-срезам; оставить поздний финальный период для независимой оценки.

## Метрики

- MAE остатков в рублях: среднее абсолютное отклонение; RMSE дополнительно для больших промахов.
- Ошибки по горизонту: 1, 7, 14, 30 дней; общий показатель с явным способом агрегации по компаниям и отсечкам.
- Разрывы: precision/recall предупреждений, ошибка даты и суммы, lead time; заранее определить правило сопоставления прогнозного и фактического эпизода.
- Если фактических разрывов нет, recall не определён, а не 100%. Неоплаченные обязательства и спасательные переводы могут скрывать проблему в EOD: отрицательный остаток — наблюдаемый критерий, не полная разметка бизнес-дефицита.
- Не использовать «100% − MAPE» как универсальный процент точности: остаток может быть нулевым/отрицательным. Не путать качество прогноза с вероятностью кассового разрыва.

Orchestrator сохраняет значения метрик, периоды, число срезов/проверенных дней, параметры и версию метода. Forecast вычисляет их и возвращает; собственной БД ему не требуется. Отдельный пользовательский переключатель бэктеста не обязателен.
