# Сервисы, HTTP-потоки и данные

## Загрузка выписки

Клиент → Gateway → PreProcessor: CSV и идентификатор организации. Gateway передаёт проверенный контекст пользователя без токена. До трудоёмкого импорта проверить право загрузки через Orchestrator, который владеет членствами; путь/заголовок companyId сам по себе прав не даёт.

PreProcessor:
- Ограничивает размер файла/число строк; не выполняет формулы и инструкции из назначения платежа.
- Проверяет кодировку, разделитель, обязательные колонки, типы дат/сумм/направлений; нормализует строки.
- Категоризует по правилам/словарям назначения и контрагента. На старте без ML; неизвестное — OTHER, не выдуманная уверенность.
- Передаёт в Orchestrator нормализованные и категоризованные операции, идентификаторы исходных строк и отчёт качества по внутреннему HTTP.
- Возвращает клиенту подтверждённый Orchestrator результат импорта. При сбое сохранения не выдаёт импорт за успешный.

Orchestrator атомарно сохраняет принятый пакет и статус импорта. Для крупных файлов возможна согласованная пакетная запись с явными статусами; partial import не должен выглядеть завершённым. Повтор сетевого запроса имеет устойчивый importId/idempotency key. PreProcessor замечает дубли в файле; Orchestrator проверяет их относительно сохранённой истории. Одинаковые поля без идентификатора не всегда означают дубль платежа.

## Особенности предоставленного датасета

CSV UTF-8 BOM, разделитель `;`, даты YYYY-MM-DD, положительный amount и direction «Поступление»/«Списание». Основные поля: company_id, operation_id, operation_date, amount, direction, counterparty_inn, counterparty_name, payment_purpose, balance_eod.

ИНН — строка с ведущими нулями. balance_eod повторяется у всех операций дня: брать один согласованный остаток на дату. Проверять переход остатка с учётом суммы потоков; расхождение отмечать, не исправлять вымышленным платежом. День без строк не всегда нулевой поток: в данных есть пропуски. Дни без операций заполнять нулём только при подтверждённой полноте периода; missing хранить отдельно. Сопоставление внешнего company_id с организацией выполняет Orchestrator, не доверяя произвольному значению файла.

## Владение данными

Auth: пользователь, контакт для входа, профиль, коды/сессии/refresh и их сроки действия. Orchestrator хранит userId владельца/участника, не пароли и не refresh.

Orchestrator:
- Организации: название, ИНН, КПП при наличии, владелец, участники/роли, выбранный счёт/валюта.
- Импорты и их статусы, отчёты качества, операции и дневные остатки.
- Категория, источник правила/версия, признак ручной корректировки. Числовая уверенность только если имеет определённый смысл; не подменять её произвольным ML-процентом.
- Плановые поступления/расходы: сумма, дата, источник, статус, оплаченная/оставшаяся часть, связь с фактом. Сохранять createdAt/knownAt и изменения для исторических срезов.
- Запуски прогнозов: asOf/cutoff, входной snapshot/fingerprint, параметры/версия алгоритма, горизонт, статус и рассчитанные дни/предупреждения.
- Запуски бэктеста: отсечки, период и версия метода, метрики, ошибки по горизонтам и показатели полноты данных.

Физическая организация PostgreSQL определяется проектом; границы владения Auth и Orchestrator сохраняются. PreProcessor и Forecast не получают доступ к их таблицам.

## Запрос прогноза

Фронт → Gateway → Orchestrator. Orchestrator проверяет доступ и формирует snapshot: ежедневная история/операции, стартовый остаток, доступные на asOf будущие планы, календарные признаки и параметры. Затем HTTP → Forecast. Forecast возвращает результат; Orchestrator сохраняет запуск и отдаёт его фронту.

Для MVP обычный HTTP с заданными таймаутами и статусами. Длительный бэктест можно оформить как устойчивое локальное задание Orchestrator со статусом и polling, без брокера. Не держать транзакцию БД во время сетевого вызова. Повторы мутаций только при идемпотентности. Ошибка Forecast не заменяется выдуманным прогнозом.

Внутренние HTTP DTO проектируются по необходимости; обязательной отдельной директории контрактов/генерации нет.
