# Gateway, сеть, код и эталоны

## Принятая схема безопасности

Клиент передаёт JWT на Gateway. Фильтр Gateway проверяет подпись, алгоритм, issuer, audience, срок и принятые правила отзыва/сессий. Неверный токен на защищённом маршруте → 401.

Перед отправкой в бизнес-сервис Gateway удаляет все входящие заголовки идентификации X-User-*/X-Auth-* (включая дубли с разным регистром), затем устанавливает канонический проверенный контекст, например X-User-Id и X-User-Roles. Роли/членства должны иметь однозначный формат. Клиентский companyId не доказывает доступ.

Удалять Authorization и auth cookies перед отправкой бизнес-сервисам. Не включать TokenRelay, копирование токенов или сервисные JWT. Сервисы не проверяют JWT, не обращаются к JWKS и не поднимают resource server; их фильтр создаёт CurrentUser/Authentication из доверенного контекста. @AuthenticationPrincipal и проверки ролей допустимы с таким principal.

Auth — исключение для code/verify/refresh/logout: он получает необходимые для жизненного цикла сессии cookie/параметры, возвращает Set-Cookie клиенту. Это не разрешает пересылать refresh в PreProcessor/Orchestrator/Forecast. CSRF/Origin при внешнем cookie API проверять на Gateway и соответствующих auth endpoints.

Сервисы доступны только из закрытой сети, с ограничениями разрешённых соединений. Не публиковать backend-порты наружу; internal endpoints не маршрутизируются извне. Общая Docker-сеть сама по себе не ограничивает её участников: нужны соответствующие сетевые правила. В этой модели разрешённый участник сети является доверенным; его компрометация позволяет подделывать контекст.

Orchestrator проверяет роли/членство и фильтрует операции по организации через CompanyScope. Отсутствующий пользовательский контекст → 401, запрещённая роль → 403, чужой ресурс → 404. Межсервисные HTTP-вызовы при пользовательской операции передают только разрешённый проверенный контекст, не все входящие заголовки. Фоновые internal операции имеют явную организацию и отдельный путь, без фиктивного admin-пользователя.

## Технический стиль

Java/Spring, Gradle KTS. В каждом сервисе — feature-first; внутри фичи application / command / query / model / repository / gateway. API-контроллер: интерфейс и тонкая реализация; DTO records Rq/Rs, Bean Validation, MapStruct. Зависимости api → application → command/query → repository. В stateless PreProcessor/Forecast repository не создавать ради шаблона.

Транзакции — в application-слое сервисов с БД; сетевые вызовы вне транзакции. HTTP-адаптер — интерфейс и реализация, RestClient, таймауты и контролируемые повторы только безопасных/идемпотентных операций. Межсервисная ошибка не откатывает уже зафиксированные изменения другой БД.

Ошибки — единый ProblemDetail/ErrorCode. Деньги BigDecimal и numeric(19,2); время через Clock. Миграции Liquibase; применённые не менять. Секреты из окружения; токены, полные персональные/финансовые данные не логировать. Конкретные версии сверять с целевой сборкой, не переносить версии из старого шаблона вслепую.
